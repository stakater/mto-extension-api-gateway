# ADR-0003: Istio-native policies and a few platform-owned EnvoyFilters; Kuadrant is the alternative

- **Status:** Proposed
- **Date:** 2026-11-16 (rewritten on 2026-11-17; the first version chose
  Kuadrant policies, see Alternatives; amended the same day after an
  independent design review; on 2026-11-19 the rate limit counts per API, and
  the tier comes from the caller's role for the API)

## Context

The gateway must check the caller's token, check the allowed-API rule, set
`x-sub` and `x-roles` from the token so a caller's copy never reaches the
backend, and limit the request rate per caller and tier.

The pattern we see in practice does this with Istio `RequestAuthentication`
and `AuthorizationPolicy`, plus three hand-written `EnvoyFilter`s (header
strip, a Lua tier lookup with Envoy's rate limit filter, a correlation ID) and
an Envoy rate limit service with Redis. Red Hat lists `EnvoyFilter` as
Developer Preview in Service Mesh 3 (M2).

What we learned on 2026-11-17:

- **Istio covers the auth part with supported APIs.** `RequestAuthentication`
  and `AuthorizationPolicy` attach to a Gateway API `Gateway` or select
  workloads by label (M6); a condition matches any value of a list claim,
  exactly or by prefix (M10); an `ALLOW` policy with no rules refuses
  everything, and `DENY` is evaluated first (M12). Istio can't attach a policy
  to an `HTTPRoute` (M6). Only removing a caller's header copy, the rate limit
  and the correlation ID need `EnvoyFilter`s. Istio has no native global rate
  limit.
- **Kuadrant uses `EnvoyFilter`s too.** On Istio, its operator creates them on
  each gateway (K7). Upstream Kuadrant therefore does not remove the support
  problem; only Connectivity Link, which is paid, does (K1, K9).
- **Kuadrant adds several components.** The Kuadrant operator depends on the
  Authorino, Limitador and DNS operators, and runs Authorino and Limitador
  (K11); every request makes a call to Authorino. A `RateLimitPolicy` reads the
  caller from an `AuthPolicy` (K10), so the rate limit can't be taken alone.
- **Hand-written filters can be tested, and the failures were our own code.**
  In a kind lab, the three filters of the pattern above applied unchanged on
  Istio 1.27.9, 1.28.10, 1.29.10 and 1.30.8. Istio did rename an internal
  route configuration in 1.28, which those filters don't match. The failures
  we found were a Lua pattern that put every caller on the lowest tier, a rate
  limit that fails open, and a list claim that reaches the backend
  base64-encoded (M11).
- The engineer who built that setup chose it over Kuadrant for the same
  reasons: fewer components, and Kuadrant's features beyond JWT and rate
  limiting are not needed.

### What the gateway must do

| Requirement | Why |
|---|---|
| Check the caller's JWT: signature, issuer, audience, expiry | only callers with a token from one of the API's issuers reach an API |
| Check the allowed-APIs claim against the API | a caller uses only the APIs it was granted (ADR-0006) |
| Set `x-sub` and `x-roles` from the token, never from the caller | the backend can trust who called |
| Limit calls per caller and tier, shared across gateway pods | protect backends; service levels per caller |

Not required: other auth methods (API keys, token introspection, client
certificates), other authorization engines (OPA, SpiceDB), data lookups during
auth, signed tokens for the backend, DNS management (`DNSPolicy`), certificate
policy (`TLSPolicy`, the chart renders `Certificate`s), and token-based limits
for AI traffic. Kuadrant offers all of these; none is a requirement today.

### What each option installs

Per cluster, beyond the Gateway API CRDs and the identity provider:

| | Istio-native (this decision) | Kuadrant |
|---|---|---|
| Operators | Service Mesh (1) | Service Mesh, Kuadrant (or Connectivity Link), Authorino, Limitador, DNS (5) |
| Mesh | istiod, istio-cni, ztunnel | the same |
| Auth service | none: the check runs in the gateway's Envoy | Authorino, called on every request |
| Rate limit service | one service that speaks Envoy's rate limit API | Limitador |
| Counter store | Redis | Redis |

Per tenant gateway:

| | Istio-native (this decision) | Kuadrant |
|---|---|---|
| Token and API check | `RequestAuthentication`, one `AuthorizationPolicy` per API; the token floor and default deny once per cluster | `AuthPolicy` (gateway and per route) |
| Headers, rate limit, correlation ID | three platform-owned `EnvoyFilter`s | `AuthPolicy` headers, `RateLimitPolicy` |
| Generated by an operator | nothing | Kuadrant's own `EnvoyFilter` on the gateway |
| Backend lock | Istio `AuthorizationPolicy` enforced by a waypoint (ADR-0007) | the same |

Kuadrant moves work from each gateway's objects to components that every
cluster runs. For the four requirements above, that adds four operators and
two services, mostly for features that are not required.

## Decision

- **Token floor and default deny, once per cluster.** The bootstrap chart
  renders two `AuthorizationPolicy`s in the Istio root namespace, selecting the
  label every tenant gateway's pods carry (set through the Gateway's
  `infrastructure.labels`): a `DENY` on `notRequestPrincipals`, one
  `"<issuer>/*"` per trusted issuer, and an `ALLOW` with no rules. They exist before any gateway,
  so no apply order opens a window (ADR-0004).
- **Token check:** a `RequestAuthentication` on each tenant gateway: the
  issuers that the tenant and its APIs use (ADR-0004), audiences, optional `jwksUri`, token read only from the
  `Authorization` header (`fromHeaders`).
- **Allowed-API rule:** one `AuthorizationPolicy` `ALLOW` per API, in the
  gateway's namespace, targeting the `Gateway`: `to.operation.hosts` = the API
  route's host, and `paths` = its path prefix or exact operations; conditions: `request.auth.claims[allowed_apis]` in
  `api.<tenant>.<api>` or `api.<tenant>.<api>.*` (ADR-0006, M10), and every
  claim mapped to a header present. **The rule checks the host and the path**
  (ADR-0005), because Istio can't attach a policy to a route; APIs on one host
  must not overlap.
- **Claim headers:** `outputClaimToHeaders` sets `x-sub` (`azp`), `x-roles`
  (`allowed_apis`) and any team extras (ADR-0012). **EnvoyFilter 1** removes
  the caller's copies of all of them, plus a platform list of reserved names
  and their underscore variants, before `jwt_authn` runs.
- **Rate limit: EnvoyFilter 2.** Envoy's rate limit filter before `router`,
  and rate limit actions at the virtual-host level, with no virtual-host or
  port name to match: one entry per API, matched on the API's host and path
  (M18). Descriptors: `tenant`, `api`, `tier` and `azp`. Each API counts
  separately, as the per-API gateways do today.
- **The tier comes from the caller's role for the API, with exact text.** As
  today, a caller has one role per API and tier, in the allowed-APIs claim.
  Envoy's expression descriptor (`envoy.rate_limit_descriptors.expr`, CEL,
  M20) checks the tiers from the highest rate down: is
  `api.<tenant>.<api>.<tier>`, or the API's old role name `<old>-<tier>`
  during migration (ADR-0006), in the claim? The first one found is the tier;
  none found gives the lowest tier. No Lua, no pattern: a name with hyphens
  can't break it. The template writes the expression so that it can't fail:
  it checks that the claim is a list, because Envoy applies no limit when an
  expression fails (M20). Tokens and the identity provider stay as they are. The rate limit service is
  deployed by the bootstrap chart and reached through Istio's documented
  outbound cluster name (`outbound|<port>||<host>`). A tenant or an API the
  platform exempts gets `unlimited` in the service's configuration, so the
  filter stays (ADR-0004).
- **Correlation ID: EnvoyFilter 3,** only when the team turns it on
  (ADR-0012): the route configuration adds the platform's correlation header
  from `x-request-id` when the caller sent none.
- **Access logs and traces:** Istio `Telemetry`, a supported API, when the
  team turns them on (ADR-0012).
- **These policies are rendered by the tenant's child `TemplateInstance`**
  (ADR-0013), never by the team's request.
- **Rules for every `EnvoyFilter` the extension renders:**
    - it selects exactly one tenant gateway (`workloadSelector`);
    - it matches only documented filter names (`jwt_authn`, `router`), or no
      name at all;
    - it has no Lua;
    - it is on an allowlist in the render check, and any other
      `EnvoyFilter`, `WasmPlugin` or `TrafficExtension` fails the render;
    - the acceptance suite runs on every Service Mesh minor upgrade before a
      release says it supports that version (G.10).
- **No Kuadrant and no Connectivity Link for now** (ADR-0011).

## Consequences

- The auth path uses supported Istio APIs, inside the gateway's Envoy, with no
  extra network call.
- No extra operators. One more workload: the rate limit service; the platform
  provides Redis.
- **Stakater owns three `EnvoyFilter`s, a Developer Preview API,** and depends
  on one Istio-generated name (the outbound cluster). A customer that needs
  Red Hat support for every part of the gateway's request path is told this
  before it adopts the extension. The upgrade suite is the mitigation.
- **APIs share a host by path, with overlap checks** (ADR-0005). Two APIs
  whose paths overlap on one host fail closed. The rule depends on Istio's
  path normalization (M16).
- No defaults-and-overrides model. "A tenant can't weaken the baseline" rests
  on three things: the floor and the default deny live in the root namespace;
  the platform renders every other gateway policy; and admission refuses a
  tenant's gateway policy, filter or gateway identity (ADR-0008).
- The rate limit counts per tenant, API, tier and caller. The child re-renders
  the rate limit filter when an API is added or removed.
- Whether the rate limit fails open or closed when its service is down is a
  platform value, documented as a limit.
- A list claim in `x-roles` arrives base64-encoded JSON; backends decode it.

## Alternatives

- **Kuadrant policies (`AuthPolicy`, `RateLimitPolicy`), on Connectivity Link
  or upstream (the first version of this ADR).** Not chosen for now:
    - several more operators, and Authorino in every request's path;
    - Kuadrant still adds its own `EnvoyFilter`s; only Connectivity Link,
      which is paid, is supported;
    - its main gain over this decision is the rate limit, and that can't be
      taken without the auth part.

  It would give status (`Enforced`), defaults and overrides, maintained Envoy
  wiring, and **policies that attach to a route**, which would make the
  path-scoped rule of ADR-0005 unnecessary. **Revisit** when a customer
  requires Red Hat support for the gateway's request path (Connectivity
  Link), or when Kuadrant installs as fewer components.
- **Hand-written `EnvoyFilter`s per team (today).** Rejected: untested custom
  code per team; the Lua tier bug went unnoticed (M11).
- **The token floor and default deny next to each gateway.** Rejected: their
  protection would depend on the order and success of every apply.
- **Istio-native only, no rate limit.** Rejected: the rate limit is a
  requirement.
- **A tier claim in the token: one `tier` per caller, or a table of tiers per
  API (`api_tiers`).** Kept as the fallback if Service Mesh's proxy lacks the
  expression descriptor (G.0). Not chosen: the identity provider and every
  token change, and a realm import gives new signing keys (design §12).
- **Today's Lua tier lookup, fixed.** Rejected: no Lua in the request path.
- **One rate limit counter per tenant, tier and caller, for all of a tenant's
  APIs (the version before 2026-11-19).** Rejected: today each API counts
  separately, so a caller of two APIs would get `429` sooner after a move, a
  change that callers of production APIs would see.
- **A separate API management product.** Rejected: out of scope (vision,
  non-goals).
